# 从“理解架构”到“守护架构”：在容易被误解的 Arm 架构中重新认识 CPU 验证的价值

——“容易被误解的 Arm 架构”主题征文点评

在 CPU 芯片研发过程中，我们经常会遇到一种现象：对于同一项 Arm 架构特性，架构、设计和验证工程师可能有着不同的理解。架构师认为已经定义清楚，设计工程师认为实现符合预期，验证工程师认为相关场景已经覆盖，但直到软件联调、系统测试，甚至芯片商用之后，才发现某些架构行为并没有真正得到保证。

为什么会出现这种情况？是架构规范不够清晰，是微架构设计存在遗漏，还是验证不够充分？

读完本期“容易被误解的 Arm 架构”专题的八篇文章，我认为，这些问题背后还有一个更加本质的原因：**我们对于架构的理解，往往停留在“特性应该如何工作”，却没有充分思考“架构究竟向软件承诺了什么，以及这一承诺在什么条件下必须成立”。**

八篇文章从 ISA 扩展、软硬件职责边界、非法软件、规范一致性，到 DIT、SIPOE2、RAS 和异常优先级，结合真实项目案例，展示了架构理解偏差如何演变为复杂的设计和验证问题。

这些文章带给我最大的启发是：**理解 Arm 架构，不仅是读懂规范，更要建立从架构规则、软件行为到微架构实现，再到验证证据的完整认知链条。** 对于验证团队而言，这也关系到我们如何定义验证边界、识别风险，以及真正保障 CPU 的交付质量。

## 一、架构的本质是软硬件契约，而不是功能特性的简单集合

第一篇《从 Arm ISA 标准到场景化扩展》提出了一个很有价值的问题：面对客户需求，是否一定需要扩展 ISA？

从产品竞争力出发，我们需要持续创新，通过差异化特性提升性能、功耗和系统能力。但从架构角度看，任何一项 ISA 扩展，都不只是增加几条指令、几个寄存器那么简单。

它可能影响操作系统、虚拟化、异常处理、安全隔离乃至整个软件生态。尤其对于通用 CPU，架构的重要价值，就是为不同软件建立稳定、可信、长期兼容的运行基础。

文章中关于嵌套虚拟化从自定义方案向 Arm FEAT_NV 标准靠拢的讨论，以及 TLBI 广播扩展的案例，很好地说明了基础架构标准化与产品差异化之间的取舍。

从验证角度看，我认为这里还可以引申出一个重要观点：**每增加一项架构能力，增加的不只是功能验证工作量，更可能是在扩大整个系统需要保证的行为边界。**

特别是当新特性与虚拟化、权限、地址转换、异常等既有机制发生交叉时，验证复杂度往往不是简单相加，而可能呈现组合式增长。

因此，验证团队不能只是被动接收 Feature List，再根据功能描述拆分测试点，而应该在架构设计阶段就主动参与方案评审，评估新增特性对整体架构语义和验证复杂度的影响。

一项好的架构创新，不仅应该有明确的业务收益，还应具有清晰的软件使用方式，以及可理解、可实现、可验证的行为边界。

**创新不是增加复杂度本身，而是在可控复杂度下创造新的价值。**

## 二、真正危险的不是“不理解”，而是“自以为理解”

第二篇《从架构行为定义到真实场景：厘清软硬件实现的边界》，给我留下了很深的印象。

文章通过硬件“多做一点”“少做一点”，以及 Arm 的定义是否一定合理三个问题，揭示了架构理解中容易被忽视的风险。

其中，共享 TLB 与 FEAT_CnP 的案例非常典型。

硬件为了更加保守，在 TLB 命中判断中引入另一个线程的寄存器状态，初衷是避免不合理的共享命中。但由于没有充分考虑线程状态变化及软件恢复寄存器的过程，这种额外判断反而引入了新的跨线程依赖，最终导致 TLB conflict fault，并在 Linux 启动中暴露问题。

这个案例说明，**硬件的“保守实现”，不等于架构行为更加安全。**

从局部设计看，多增加一个检查条件似乎能够降低风险；但站在整体架构视角，它可能改变状态依赖关系，创造出原先不存在的复杂场景。

反过来，DSB 与 out-of-context translation table walk 的案例则提醒我们，架构中看似抽象的完成性保证，并不是可有可无的要求。如果硬件没有严格落实，某些问题可能直到复杂软件操作序列出现时才被触发。

这里也体现了一个值得验证团队反思的问题：我们在验证中经常将设计实现作为理解架构的参考，但如果设计本身就建立在不准确的架构假设上，那么验证很容易与设计形成相同的认知盲区。

最终出现的不是设计没有通过验证，而是**设计和验证共同验证了一个错误的理解。**

这也是为什么我始终认为，验证团队必须保持相对于设计实现的独立判断能力。面对复杂架构行为，不能简单以“设计就是这么实现的”或者“历史项目一直如此”为依据，而应该追问架构为什么这样要求、软件究竟依赖什么保证，以及现有实现是否引入了额外的行为依赖。

第四篇《三种表达，一个架构》关于 Rule、Description 与 Pseudocode 不一致的讨论，也从另一个角度说明了这一点。面对规范歧义，我们既不能自行选择最容易实现的解释，也不能盲目依赖某一份参考模型，而应追溯架构意图，通过官方澄清建立统一认识。

**验证的独立性，首先是架构认知的独立性，而不仅仅是验证环境和设计代码的独立。**

## 三、从“非法软件”走向“架构边界”，是验证思维的一次重要升级

第三篇《从“非法软件”到“架构边界”》，直接触及了验证工作中一个长期存在的认识误区。

在实际项目中，我们常常会听到这样的判断：

“正常软件不会这么操作。”

“这个指令序列不符合软件规范。”

“下游确认不会出现这种场景，因此没有必要验证。”

这些说法在特定产品场景下可能有一定参考价值，但对于通用 CPU 而言，并不能天然成为验证裁剪的依据。

CPU 面对的是开放的软件输入空间。我们不仅要考虑当前已知的软件，还需要考虑未来软件、存在缺陷的软件，甚至主动构造恶意指令序列的软件。

尤其在云计算和虚拟化环境中，Guest OS 不一定可信。一个租户运行的不合理指令序列，不应该突破权限与安全边界，更不应该影响其他租户的正常运行。

文章将架构承诺划分为三个层次：单指令的确定性行为、特定指令序列形成的架构效果，以及 CONSTRAINED UNPREDICTABLE 行为下仍然必须坚守的底线。

我非常认同这一划分。它实际上为验证边界提供了一种更准确的定义方式。

过去我们容易以功能点和场景覆盖率为中心构建验证计划，关注哪些指令执行过、哪些寄存器组合覆盖过、哪些功能场景已经命中。

但对于复杂架构，真正需要回答的是：**哪些行为必须发生，哪些行为允许发生，而哪些行为无论如何都不能发生？**

特别是最后一类，往往对应权限隔离、安全保护、状态一致性以及系统活性等关键不变量。

例如，某些错误的软件序列可以导致功能结果不确定，但不能因此获得不应拥有的访问权限；某个 Guest 可以持续执行特殊维护指令，但不应因此无限期阻塞其他 Guest 的正常执行。

这类要求仅依靠传统随机激励和指令级比对，并不容易完整验证。

因此，验证方法学需要从传统功能正确性验证，进一步扩展到架构性质验证。通过 Formal Property Verification、系统级不变量以及针对非预期软件行为的定向测试，验证架构保证的行为边界。

**我们不可能穷举所有软件，但可以努力证明那些无论软件如何变化都必须成立的架构承诺。**

这是验证工作从“覆盖功能”走向“守护架构”的重要转变。

## 四、复杂架构的风险，往往隐藏在特性交叉和真实业务场景中

本期关于 DIT、SIPOE2、RAS 和异常优先级的几篇文章，则从不同角度展示了复杂架构风险的特点。

DIT 的演进提醒我们，单条指令满足数据无关时序约束，并不意味着整段程序自然具备同样的安全保证。数据相关预取、分支投机等微架构行为，都可能引入指令级功能比对难以发现的安全风险。

SIPOE2 的案例则说明，新特性看似只是对传统 Permission 机制的扩展，实际上却引入了指令侧与数据侧之间新的权限依赖。PLBI、IRTSync 等机制涉及复杂的同步关系，容易在与原有架构交叉时产生死活锁、属性遗漏及异常优先级问题。

RAS 相关案例同样值得深思。硬件即使符合架构允许的错误处理方式，也未必能满足真实业务对可靠性和可用性的要求。例如 Poison 引发的异常风暴，在某些产品场景下可能使局部错误演变为系统级可用性问题。

这些案例共同说明：**架构合规是产品质量的重要基础，但不等于产品质量的全部。**

对于复杂新特性，我们不仅需要验证它新增了什么，还需要重点分析它改变了哪些历史假设、引入了哪些新的状态依赖，以及在真实业务场景中可能产生什么系统级影响。

这要求验证团队进一步强化架构、设计、软件和系统之间的协同，把验证视野从单一模块扩展到整个软硬件系统。

## 五、把架构理解转化为可持续的质量保障能力

综合八篇文章，我认为最值得我们思考的，不是记住某一条 Arm 架构规则，而是如何把这些经验沉淀为团队能够持续运转的验证方法学。

首先，要推动架构风险识别前移。在新特性开发初期，就由架构、设计、验证及必要的软件团队共同梳理架构行为边界，重点识别新增状态依赖、跨模块交互以及容易产生歧义的规范描述。

其次，要从功能覆盖走向架构保证。除了传统 Feature Coverage，还需要围绕功能正确性、权限安全、状态一致性、同步完成和系统活性等要求建立验证策略。将随机仿真、Formal 验证和 EMU/FPGA 原型验证等手段有机结合，为关键架构承诺提供充分的验证证据。

再次，要重视历史经验的持续沉淀。架构 Issue、历史 Errata、Late Bug 以及软件联调问题，都不应只停留在问题单中，而应该反向推动验证需求更新，尽可能固化为可复用的 Checker、Formal Property、回归用例和评审规则，避免同类问题跨项目、跨版本重复出现。

最后，也是我认为最重要的一点：**要培养一支敢于质疑、善于追问、能够独立分析架构问题的验证队伍。**

面对模糊的架构描述，不能满足于“以前都是这么做的”；面对设计给出的解释，不能止步于“逻辑上说得通”；面对软件团队反馈的问题，也不能简单归因于“软件使用不规范”。

真正优秀的验证工程师，需要能够从微架构实现反推架构语义，从异常现象还原真实软件场景，从局部功能扩展到系统级风险。这种能力不是依靠增加测试数量就能获得的，而需要长期的架构学习、问题复盘、跨团队交流和项目实践。

## 结语：验证的最终价值，是让架构承诺真正可信

回到本期“容易被误解的 Arm 架构”主题，我认为八篇文章最有价值的地方，在于作者们没有停留在架构条文的表面解释，而是结合真实工程实践，不断追问隐藏在规则背后的设计动机、软件需求和系统风险。

这些文章也再次提醒我们，随着 CPU 微架构日益复杂、Arm 架构持续演进，依赖个人经验、局部功能覆盖和后期软件联调兜底的验证方式，将越来越难以满足高质量交付要求。

对于验证团队而言，未来的核心竞争力，不只是能够搭建多大规模的验证环境、运行多少条随机指令、达到多高的覆盖率，而是能否真正理解架构承诺，提前识别设计和规范之间的认知偏差，并以充分可信的验证证据证明这些承诺已经落实。

**好的设计，是用高效的微架构实现架构承诺；好的验证，则是用独立而严谨的证据守护这份承诺。**

希望本期专题能够成为一个起点，引导更多同事从日常设计和验证工作中发现那些容易被忽视的架构问题，把对架构的理解从“知道规则”提升到“理解本质”，再从“理解本质”转化为“保障质量”的实际能力。

**真正值得追求的，不是让团队永远不再产生架构误解，而是建立一套能够更早发现误解、更快澄清分歧、更有效防止问题重复发生的技术与质量体系。**
